# Design

## Context

`internal/server/server.go` authenticates, calls `proxy.Prepare`, forwards, and emits a deferred `slog` summary. Its response wrapper already tracks status and preserves Flush/Unwrap/Hijack. `Prepare` may read and replace the body for model alias routing. `internal/proxy/proxy.go` uses `httputil.ReverseProxy` with immediate streaming flush and a generic 502 error handler. Both ordinary and encrypted listeners use the same server assembly, but no conversation storage exists.

The feature must capture actual content without changing this forwarding contract. A file corresponds to one authenticated HTTP call, not a multi-turn session. No new API, database, client header, or external library is required.

## Decisions

- **Configuration:** add `conversation_log: {enabled, directory, max_body_bytes}` with defaults false, `logs/conversations`, and 8388608 bytes per body. Distinguish omitted limits from explicit zero. Parse configuration independently of filesystem access; `Load` resolves relative directories against the absolute configuration-file parent. Startup builds an optional shared recorder and passes it to both listeners through backward-compatible server options/constructors. Filesystem initialization failure logs safely but does not prevent serving; later finalization attempts can retry directory creation. Disabled logging performs no storage initialization or capture.

- **Capture boundary:** after successful key authentication, allocate an internal random 128-bit request ID and install a bounded read/close wrapper on the original body before `Prepare`. Reads populate a prefix buffer and count observed bytes; EOF/read errors track completeness. Do not re-wrap the replayed or rewritten body, or bytes would be duplicated or the alias replaced in the record. Known content length may establish complete consumption when a reader stops exactly at that length without an extra EOF read. Unknown length requires observed EOF. Never drain an unread remainder merely for logging. Record the original escaped path before any mutation; exclude queries entirely.

- **Response capture and failure observation:** extend the existing response writer to observe successfully written bytes (only `n` bytes when Write partially succeeds) and write errors while preserving Flush, Unwrap, informational statuses, and existing behavior. Add a per-request internal observer passed through context to the reverse proxy: a response-body read wrapper reports EOF versus unexpected read errors, and ErrorHandler reports a sanitized transport failure category while preserving its existing 502 response. Finalization also checks context cancellation. Successful handler return alone is insufficient evidence of complete streaming delivery. A known-length response fully consumed without EOF may count as complete. No response bytes means explicit empty capture, not missing data. Hijacked connections, if encountered, are marked unsupported/incomplete rather than claimed as captured conversations.

- **Finalization on all exits:** create a deferred finalizer before `Prepare` so 400/413 and 502 responses are included. Observe panic/ReverseProxy abort paths, attempt to write a partial record, then preserve/rethrow the original panic so net/http behavior stays unchanged. Do not invent a 200 status if no final status was committed on an aborted request. Use concurrency-safe body capture snapshots because transport request reads/close can overlap handler cleanup. Add request ID to existing operational request summaries for captured calls; do not add it to client or upstream headers.

- **Versioned JSON:** version 1 records contain `request_id`, `started_at`, `ended_at`, `duration_ms`, request method/path, optional upstream origin and model ID/name, optional final status, response completion, and an optional error category. Each request/response body has `data`, `encoding` (`utf-8` or `base64`), `observed_bytes`, `captured_bytes`, `truncated`, and `complete`. Body capture is a byte prefix; encode invalid UTF-8 prefixes as base64 so binary data and partial UTF-8 sequences are lossless. Preserve raw compressed bytes and raw SSE rather than decompressing or reconstructing assistant messages. Truncation is independent of transfer completion; observed size is not asserted to be total size for unread bodies. Do not persist HTTP headers; this version treats body bytes as opaque content.

- **Persistence:** introduce `internal/conversationlog` for bounded captures, record schema, ID/clock generation, and file storage. Use UTC start time for `YYYY-MM-DD/HHmmss_<id>.json`. Create private directories (0700) and exclusive owner-only temporary files (0600) in the destination date directory; serialize and close before publishing the final `.json`. Use a non-overwriting publication strategy on supported OSes (for example same-directory hard-link publication followed by temporary unlink); a collision generates a new filename rather than replacing a record. Clean temporary files on ordinary errors. Keep filesystem functions injectable for failure tests. Existing directories are not silently chmodded; operators remain responsible for ACLs, symlinks, and secure parent directories. No file path is derived from a client body/header.

- **Bounded buffering rather than synchronous per-chunk disk writes:** keep at most the configured prefix for each body in memory, forward bytes immediately, then serialize one record synchronously after forwarding ends. This avoids disk backpressure during SSE and background queues that can drop records or complicate shutdown. Finalization remains inside the active handler so normal graceful shutdown covers it. JSON encoding has bounded additional allocation overhead; aggregate memory scales with active requests, not just one limit. This is not a durable in-progress journal.

- **Coordinated listener shutdown (approved follow-up):** keep a completion channel for the encrypted server's `Serve` lifecycle. When the ordinary server returns, cancel the shared lifecycle context and wait for the encrypted lifecycle to finish before returning from main or taking the ordinary-server error exit. An encrypted-server failure still logs its error and cancels the shared context, as before. Both listeners drain concurrently with their existing 10-second shutdown budgets; waiting for both must not introduce an unbounded new drain or a background logging queue. This ensures an idle ordinary listener cannot end the process while an encrypted call is still finalizing. Cover active encrypted streaming during cancellation and ordinary startup-failure cancellation with regression tests.

- **Security and failure policy:** omit headers, query strings, tokens, complete configuration objects, and raw transport errors. Whitelist categories such as `preparation_failed`, `upstream_transport`, `upstream_read`, `client_write`, `canceled`, and `aborted`. Persistence diagnostics contain request ID, operation, and safe error category, not raw payloads or arbitrary path/error strings. Logging failures must never replace a client response, retry a provider, or fail gateway startup. Body data itself is deliberately unredacted. Existing `--log-file` continues controlling operational logs only.

- **Retention and scope:** defaults and the 8 MiB cap are initial design choices, not an unlimited full-history guarantee. This version has no automatic retention/deletion, provider-aware parsing, multi-call grouping, or crash recovery. Document manual/OS-managed pruning, storage growth, and decrypted peer content being stored in plaintext at rest. Each gateway logs its own hop independently.

## Risks / Trade-offs

- Bounded capture can omit part of a long reply. Explicit truncation and separate completeness flags make this visible; operators may raise the limit at a memory cost.
- No guarantee is made for forced termination, process crashes, or shutdown timeout during persistence. Temporary files may remain, and active calls may lack records. Atomic publication prevents ordinary readers from mistaking partial JSON for a finished record.
- Slow storage can delay handler cleanup after the response was forwarded. No background worker is introduced initially; benchmark finalization and revisit if operational evidence warrants it. Fail-open isolates errors, not arbitrarily stalled filesystem calls.
- File growth is unbounded over time even though individual records are bounded. Operators must provision disk and retention externally; automatic pruning is deferred to avoid silently deleting user conversations.
- POSIX permission modes do not establish restrictive Windows ACLs. Documentation must cover ACL setup, and tests must avoid promising Unix permissions on Windows.
- Transport observation and response wrappers can accidentally change streaming or hide disconnects. Integration tests must verify an early flushed chunk, truncated upstream streams, partial writes, and encrypted-listener parity before release.
